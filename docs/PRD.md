# BY Credit · 越南手机分期录单与订单管理 PRD

> 版本 1.1 · 分两阶段实施：先完成系统主体与演示闭环，后接真实支付和签约服务
> 产品形态：Web 后台（供业务员/审核/财务/运营使用）+ Zalo 小程序内嵌 H5（供客户查账还款）
> 部署：同一服务器 `byphone.cn`，按路径前缀拆分（见 DESIGN.md）

---

## 1. 业务范围与实施阶段

### 1.1 第一阶段：系统主体 + 演示闭环

- 业务员录单 → 初审 → 演示签约 → 终审 → 财务放款 → 客户还款 → 贷后管理
- 门店管理（合作/自有、A/B/C/D 评级、正常/冻结）
- 8 角色权限框架（按动作级权限配置）
- MDM 监管锁绑定（双字段：序列号 + IMEI 都必填，准富后台手动操作，系统只记录结果）
- 电子签约演示：发起、待签约、成功/失败回填、重新签约，以及与订单状态机的完整联动
- 支付演示：还款入口、支付状态查询、成功/失败模拟，以及与真实回调共用的统一销账逻辑
- 账单四字段（首付款/分期额/期数/每期金额）+ 每期代客登记 + 账单合并对账
- 现金、普通转账的人工还款登记（不依赖第三方支付，第一阶段即为真实业务功能）
- 财务报税 CSV 导出
- 操作日志（所有人可见，只增不删）
- 客户 H5 的订单、账单和还款状态查询；支付按钮在演示环境明确标注为演示功能

第一阶段不接真实 VietQR 或 MobiFone 服务，不生成真实付款二维码，不创建真实合同，也不发送真实签约短信。演示功能仅用于开发和演示环境。

### 1.2 第二阶段：第三方真实对接

- **VietQR**：token、真实二维码、支付短码与 content、回调、主动查单、二维码过期、幂等销账和异常对账
- **MobiFone eContract**：按最终确认的 JSON/模板方式创建合同、手机登录与短信、合同及签署人 Webhook、状态映射、失败重试和 PDF 下载转存
- 真实适配器接入后，复用第一阶段的订单状态机、签约结果处理、统一销账、权限和日志，不重写主体业务

### 1.3 明确不做（两个阶段均不做）

- 违约金
- 门店代收
- 商品库/SKU（录单直接选机型和容量）
- 老客户资料复用进件（每次重新提交）
- 准富以外的 MDM 自动绑定/锁机回调（无开放 API）
- 投诉管理、回收管理
- 未经服务商确认的退款、VA 虚拟账户等扩展能力不提前开发

## 2. 订单状态机（14 态）

```
draft → pending_first → pending_customer_sign → pending_final → approved_final → pending_finance → pending_payout → repaying → closed
           ↓                   ↓                  ↓
    rejected_first         rejected_final      cancelled
                                          ↘ overdue → breach
```

| 状态 | 含义 | 谁能触发 |
|---|---|---|
| draft | 草稿 | 业务员 |
| pending_first | 待初审 | 业务员提交 / 驳回后补件重提 |
| rejected_first | 初审驳回 | 初审 |
| pending_customer_sign | 待客户签约（第一阶段为演示） | 初审发起签约 |
| pending_final | 待终审 | 客户签约成功且 MDM 已绑定 |
| rejected_final | 终审驳回 | 终审 |
| approved_final | 终审通过待财务 | 终审通过 |
| pending_finance | 财务待审批 | 系统自动流转 |
| pending_payout | 待放款 | 财务审批通过 |
| repaying | 还款中 | 财务录入回单 |
| overdue | 逾期 | 系统定时任务判定到期未还 |
| breach | 坏账 | 财务/贷后手动标记 |
| closed | 结清 | 最后一期还款成功 |
| cancelled | 取消 | 管理员 |

状态机两个阶段保持一致：第一阶段的签约和线上支付状态由演示适配器触发，第二阶段仅把触发来源替换为真实服务商回调或主动查询结果，不改变订单流转规则。

## 3. 8 角色 + 动作权限

| 角色 | 主要动作 |
|---|---|
| admin（管理员） | 全权限 |
| sales（业务员） | 录单、补件重提、查看自己的订单进度 |
| first（初审） | 初审通过/驳回、上传客户资料、发起签约、回填/异常处理签约结果、绑定/解绑 MDM、改账单四字段、改首期还款日 |
| final（终审） | 终审通过/驳回 |
| finance（财务） | 审批放款、录入放款回单、代客登记还款、延期、坏账标记、CSV 导出 |
| manager（店长） | 看本店数据、编辑本店资料 |
| aftercare（贷后） | 查看对账、添加对账备注 |
| collector（催收） | 查看逾期/坏账订单 |

权限按动作名配置，集中在 `assets/shell.js` 的 `PERMISSION_GROUPS`。新增角色只需追加条目，不改代码逻辑。

## 4. 账单四字段与修改权限

四字段：`downPayment`（首付款）/ `principal`（分期额，= 售价 - 首付款）/ `periods`（期数）/ `perPeriod`（每期金额）

- 初审**未通过**：初审和管理员可以改
- 初审**已通过**：仅管理员可改
- 所有修改留日志（谁、改前改后、时间）

还款日：直接改首期还款日，后续各期整月后移，原因必填，留日志。

## 5. 支付与还款

### 5.1 三种支付渠道
- **线上 QR**：第一阶段使用明确标识的演示支付；第二阶段切换为 VietQR 真实二维码，回调或主动查单确认后自动销账
- **其他转账**：银行 App / 电子钱包转账到对公账户 → 代客登记 + 财务对账（第一阶段实现）
- **线下现金**：现金交付 → 代客登记（第一阶段实现）

### 5.2 每期账单代客登记
必填：支付订单号、支付渠道、支付时间。现金/转账渠道不能只填金额就过。

### 5.3 统一销账与演示支付（第一阶段）
- 建立内部支付请求，关联订单、账单期次、金额、支付渠道和支付状态。
- 演示成功、真实服务商回调、主动查单补账均调用同一个内部销账服务，禁止各写一套账单更新逻辑。
- 销账后更新账单的已还金额、支付时间、交易号和渠道；最后一期完成后将订单流转为 `closed`。
- 演示支付必须有 `mock` 来源标识和演示交易号，重复模拟不得重复销账，且不得进入真实财务统计。

### 5.4 VietQR 适配规则（第二阶段）
- 根据最终确认的服务商规则，在 VietQR 适配器内生成 `orderId` 短码和 `content`，不写进订单核心服务。
- 已知限制为 `orderId` 不超过 13 字符、`content` 不超过 23 字符且无声调、无特殊符号；具体拼接和唯一性规则待联调确认。
- 二维码有效期、过期后的查单与禁用逻辑由支付适配器和支付请求状态共同处理。

### 5.5 幂等与异常处理
- 第一阶段即建立“支付渠道 + 外部交易号”的幂等约束，同一笔交易只销一次账。
- 第二阶段真实回调按最终确认的交易唯一字段幂等；金额不符、订单找不到等情况只记录异常，不直接销账。
- 重复回调返回成功响应，但不重复更新账单或订单。

### 5.6 回调丢失兜底（第二阶段）
- 优先接入服务商最终确认的 `check-order` / 主动查单能力，与回调共用统一销账服务。
- 对长时间未销账的支付请求提供财务人工核对入口。
- 是否定时拉取或导入银行流水，待服务商能力和账户权限确认后决定，不默认采用爬取商户后台方案。

## 6. MDM 监管锁

- 双字段都必填：序列号 + IMEI
- 准富后台需短信验证码，无法代登，所以**不在我们系统里绑定/锁机**
- 系统只记录"人工绑定结果"（谁、什么时候、填了什么序列号和 IMEI）
- 解绑必须填原因，留日志
- 准富回调什么都不依赖，我们不假设

---

## 7. 电子签约（第一阶段演示，第二阶段接 MobiFone）

### 7.1 第一阶段：演示签约与统一结果处理

1. 初审在允许签约的订单状态下发起签约，系统创建签约次数并进入 `pending_customer_sign`。
2. 演示适配器不调用外部服务；初审或管理员可回填演示结果：成功必须填合同号，失败必须填原因。
3. 成功和失败都调用统一的签约结果处理服务：签约成功 + MDM 已绑定 → 转终审；签约成功但 MDM 未绑定 → 回初审补齐绑定；签约失败 → 退回初审补件或重新签约。
4. 所有发起次数、合同号、失败原因、操作人、状态前后值记进日志。
5. 页面明确标注“演示签约”，演示合同号带 `mock` 来源标识，不视为真实法律合同。

### 7.2 第二阶段：MobiFone 真实适配器

- 按服务商最终确认的 JSON/模板接口创建合同，模板 ID、字段映射和签署配置集中放在适配器配置中，不进入订单核心逻辑。
- 按确认后的手机登录机制触发短信，不自行假设或另建短信流程。
- 接收合同级、签署人级 Webhook，将外部状态映射为内部统一状态后调用同一签约结果处理服务；必要时以主动查询补状态。
- 外部回调必须验明来源并幂等处理；服务商原始状态、外部合同号和原始回调留档。
- 签约成功后立即下载并转存 PDF，不能长期依赖服务商临时链接。
- 人工回填能力保留为异常处理手段，但真实环境下必须记录操作人和原因。

## 8. 客户小程序

- 用客户手机号精确匹配订单（`bycredit_customer_phone`）
- 默认读 Zalo 绑定的手机号
- 右上角换绑入口（客户多个手机号可能）
- "我的订单" 列表 + 每期账单状态（第一阶段实现）
- 还款入口沿用后端 `/api/payment/generate` 和支付状态查询契约：第一阶段返回明确标识的演示支付信息，第二阶段切换为 VietQR 真实二维码 + `qrLink`，真实到账确认后刷新状态

## 9. 门店

- 类型：合作店铺 / 自有店铺
- 状态：正常 / 冻结（冻结后不可录新单、不可送财务，存量继续还款）
- 评级：A 正常 / B 影响放款比例 / C 影响放款比例 / D 黑名单
- 自有店铺不签回收协议，但门店合同仍须上传
- 评级/冻结变更必须填原因，留日志

## 10. 历史客户风险

审核界面按相同证件号查询历史订单：
- 正常还款中/结清 → 绿色
- 逾期/坏账 → 红色
- 标注"存在历史订单"并列出笔数

## 11. 数据层约定

### 所有操作都记日志
统一结构：
```js
{ id, at, by, role, action, before, after, note }
```
只增不删，所有人可看。

### 外部服务与演示数据约定

- 支付请求预留：内部请求号、订单/账单、金额、渠道、状态、服务商、外部交易号、过期时间、原始响应和异常原因。
- 签约记录预留：内部签约次数、服务商、外部合同号、内部统一状态、服务商原始状态、失败原因、PDF 地址和原始回调。
- 外部服务商的订单短码、模板 ID、token、状态文字和回调报文只存在于对应适配器，不进入订单核心服务。
- 所有 mock 支付和签约记录必须带明确来源标识；演示环境使用独立数据库或独立数据集，不得混入真实财务统计。
- 生产环境禁止开启 mock 成功入口；第一阶段只部署开发/演示环境。

### 财务报税 CSV（UTF-8 BOM）
17 列：订单号、客户名、证件号、手机号、门店、机型、容量、IMEI、订单金额、首付款、分期额、放款金额、已回款、未回款、放款时间、银行回单号、订单状态。

## 12. 第一阶段验收闭环

必须在开发/演示环境完整走通：

```text
录单 → 初审 → 演示签约 → MDM 登记 → 终审 → 财务放款 → 生成账单
     → 演示线上还款或人工还款登记 → 最后一期结清
```

同时验证：签约失败重签、MDM 未绑定不能终审、重复支付不重复销账、金额异常不销账、各角色越权操作被拒绝，以及所有关键状态变化均有日志。
